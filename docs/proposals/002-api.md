# Headscale API redesign

**Status:** draft, for discussion. This PR exists so we can shape the design together. It is not meant to be merged as-is.

Headscale has two HTTP APIs today, and neither is a good base for the future.

- `/api/v1` is the admin API. Its shape comes from the old gRPC gateway: verbs and arguments in paths, three ways to name a target, one node that looks different from call to call. Web UIs match on error text, because an error does not say which rule was broken.
- `/api/v2` follows the Tailscale API so that the Tailscale Terraform provider, `tscli` and the Kubernetes operator work. It can only have what Tailscale has, in Tailscale's shape.

This proposal adds a third API, made for Headscale: resource based, built with Huma, with an OpenAPI document and a generated client. The new CLI ([001], [#3375]) uses only this API. The old `/api/v1` is frozen and then removed. Breaking changes are allowed.

It was checked against the calls that the web UIs in [the web UI list](../ref/integration/web-ui.md) make today. [Checked against the web UIs](#checked-against-the-web-uis) has the result: what v0 covers, and what it does not.

## Words used here

The words are the words of [001]. The API and the CLI use one vocabulary.

| Word          | Meaning                                                                                                      |
| ------------- | ------------------------------------------------------------------------------------------------------------ |
| v0            | the new API, at `/api/headscale/v0`                                                                          |
| legacy API    | today's `/api/v1`                                                                                            |
| Tailscale API | `/api/v2`, which follows Tailscale's public API                                                              |
| resource      | a stored thing with an ID: a node, a user, an auth key, an API key, an OAuth client                          |
| collection    | all resources of one kind, for example `/nodes`                                                              |
| action        | an operation that is not create, read, update or delete, for example "expire"                                |
| name          | of a node: the name it has in headscale, used by MagicDNS. 001 says "given name", the legacy API `givenName` |
| hostname      | the name a node reports about itself; headscale cannot change it (the legacy API: `name`)                    |
| owner         | who a node or key belongs to: one user, or a set of tags, never both                                         |
| auth key      | a key a node uses to join (the legacy API: "pre-auth key")                                                   |
| API key       | a key a program uses to call the API                                                                         |
| OAuth client  | an ID and secret that mint short-lived, scoped access tokens                                                 |
| auth request  | a short-lived request from a node, named by its auth ID: a registration or an SSH check                      |
| problem       | an error response, in the format of RFC 9457                                                                 |

The examples use the people and nodes of 001: User 3 `alice`, User 4 `bob`, User 5 `carol`, Node 12 `mynode` (owned by alice), Node 13 `builder` (tagged `tag:ci`, `tag:build`). "Now" is 2026-11-10 09:14 UTC.

## Principles

1. **One resource, one shape.** A node is the same object in a list, in a get and in the answer to every write. It carries everything a client shows: owner, routes, online state, client version.

1. **One way to name a target.** A resource is named by its ID, in the path. Names, emails and prefixes are filters on a list, never a second kind of ID.

1. **Standard methods first.** `GET`, `POST`, `PATCH`, `PUT` and `DELETE` on collections and resources. An action gets its own path only when it is not a field change.

1. **A program never has to read prose.** Every error has a stable code. Every state a client must branch on is a field or an enum, not something to compute from timestamps and not a text to match.

1. **Nothing is silently ignored.** An unknown body field, an unknown query parameter and a field that cannot be changed are errors.

1. **The CLI is the first client.** A command of 001 finds its target and then makes one call. If the CLI needs to join, count or guess, the API is wrong.

1. **Headscale words.** `/api/v2` speaks Tailscale ("device", "tailnet", `enabledRoutes`). v0 speaks Headscale ("node", "approved routes"). There is no tailnet segment in a path.

1. **Change is announced.** v0 may change in any release. Every such change is in the changelog, and nothing changes without a note.

## The three APIs

| API       | Path                 | Code                         | Rule                                                            |
| --------- | -------------------- | ---------------------------- | --------------------------------------------------------------- |
| legacy    | `/api/v1`            | `hscontrol/api/v1`           | frozen and deprecated when v0 ships; removed two releases later |
| Tailscale | `/api/v2`, `/api/v3` | `hscontrol/api/v2`           | only what Tailscale has, in Tailscale's shape                   |
| Headscale | `/api/headscale/v0`  | `hscontrol/api/headscale/v0` | this proposal; may change in any release until it becomes `v1`  |

**`/api/v*` is reserved for the Tailscale API.** `/api/headscale/` holds every Headscale API. When v0 is stable it becomes `/api/headscale/v1`.

**Why the paths are what they are:**

- The Tailscale API cannot move under a prefix such as `/tailscale/api/v2`. The Terraform provider, `tscli`, the Go client and the OAuth flow of the Tailscale client all accept a base URL with a path. The Kubernetes operator is different: it has one setting, `OPERATOR_LOGIN_SERVER`, and uses it both as the API base and as the control server of the nodes it creates. A path in that URL would also move the control endpoints those nodes call (`/key`, `/machine/register`, `/machine/map`). So `/api/v2` stays at the root, next to them.
- The legacy API cannot move. The web UIs have `/api/v1` in their code.
- A new API at `/api/v0` would have no next step. `/api/v1` is taken by the legacy API, and using that path again with a new shape would break the web UIs without an error. `/api/v2` and up belong to Tailscale.
- `/api/headscale/v0` stays under `/api`, so reverse proxies that forward `/api` keep working.

**The Tailscale API gets no Headscale endpoints.** An endpoint that Tailscale does not have could collide with one they add later. `hscontrol/api/v2/README.md` allows such an endpoint today; that sentence goes. The CLI does not call `/api/v2` at all.

**"Frozen" for the legacy API means:** no new operations and no change to the wire shape. v0 and the legacy API call the same server code, so a fix there reaches both. Two changes that 001 asks for reach the legacy API this way: deleting a user also deletes the user's API keys, and `approve` refuses a registration.

The shape that is frozen must be the shape of 0.29. See [Implementation notes](#implementation-notes).

**Tools that do not use the HTTP API.** [Headscale Panel] speaks gRPC, which 0.30 removes. [ouroboros] and the local mode of [unraid-headscale-admin] run the `headscale` command and read its JSON, which 001 changes. Neither is caused by this proposal. v0 is what they can move to.

## Conventions

These hold for every operation. A resource section only says where it differs.

### Paths

- The base is `/api/headscale/v0`. The paths below leave it out.
- Collections are plural and in kebab-case: `/nodes`, `/users`, `/auth-keys`, `/api-keys`, `/oauth-clients`, `/auth-requests`, `/tags`.
- A resource is `/{collection}/{id}`.
- Collections are flat. There is no `/users/3/nodes`. A tagged node has no user, so it would have no path there. Use `GET /nodes?user=3`.
- The policy is one document: `/policy`.

### Methods and status codes

| Operation | Request                   | Success | Body                                  |
| --------- | ------------------------- | ------- | ------------------------------------- |
| list      | `GET /nodes`              | 200     | `{"nodes": [...]}`                    |
| get       | `GET /nodes/{id}`         | 200     | the resource                          |
| create    | `POST /users`             | 201     | the resource, and a `Location` header |
| update    | `PATCH /nodes/{id}`       | 200     | the resource after the change         |
| replace   | `PUT /policy`             | 200     | the document after the change         |
| delete    | `DELETE /nodes/{id}`      | 204     | none                                  |
| action    | `POST /nodes/{id}/expire` | 200     | the resource after the action         |

- **Every write returns the whole resource**, with its computed fields. A client never needs a second call to show the result.
- A delete of something that is already gone is `404`.
- An action on an auth request answers `204`: the request is gone once it is answered.
- The one delete with a body is the user delete, which reports what it removed. See [Users](#users).

### IDs

- **Every ID is a string**, in bodies, paths and query parameters: `"id": "12"`.
- An ID is opaque. A client compares it for equality and does nothing else with it. Node, user and key IDs are decimal numbers today. OAuth client IDs are hex. Auth IDs are long random strings.
- A resource has exactly one ID. A path takes only that ID, never a name.

### Update with PATCH

`PATCH` changes the fields that are sent and leaves the others alone. The rules are those of JSON Merge Patch (RFC 7396):

- A field that is left out does not change.
- `null` clears a field. It is allowed only where "no value" has a meaning. `"expiry": null` on a node means "never expires".
- An empty string clears an optional text field. `"email": ""` on a user removes the email. A `name` cannot be empty (`invalid_field`).
- A list is replaced as a whole.
- A field that cannot be changed (`id`, `created`, `hostname`) is an error, not ignored.
- A body with no fields is an error (`empty_patch`).
- All fields of one request change together, or none does.
- The body has the media type `application/merge-patch+json`. `application/json` is accepted too.

```
PATCH /nodes/12
{"name": "web-1", "expiry": null}
```

### Actions

An action is a `POST` to a path under the resource: `POST /nodes/12/expire`. It returns the resource after the action.

An action exists only for something that is not a field change: it uses the server's clock, it talks to the node, or it cannot be undone. Changing a name is not an action. The full list:

| Action                              | Why it is not a field                               |
| ----------------------------------- | --------------------------------------------------- |
| `POST /nodes/{id}/expire`           | "now" is the server's clock; the node is logged out |
| `POST /nodes/{id}/update-client`    | asks the node to update itself                      |
| `POST /auth-keys/{id}/revoke`       | cannot be undone                                    |
| `POST /api-keys/{id}/expire`        | "now" is the server's clock                         |
| `POST /auth-requests/{id}/register` | answers a waiting node and creates a node           |
| `POST /auth-requests/{id}/approve`  | answers a waiting node                              |
| `POST /auth-requests/{id}/reject`   | answers a waiting node                              |
| `POST /policy/reload`               | reads the policy again from where it is stored      |

### Lists

- A list is an object with one key, the name of the collection: `{"nodes": [...]}`, `{"users": [...]}`, `{"authKeys": [...]}`. It is never a bare array, so the answer can gain fields later.
- **A list returns everything.** There is no paging in v0. Headscale holds every node in memory, and a tailnet has thousands of nodes at most.
- If paging is added, it is opt-in: a client asks for it with `pageSize`. A client that does not ask keeps getting everything. Paging that is on by default would make a small web UI lose every row after the first page, without an error.
- The order is fixed: nodes, users and keys by ID as a number, OAuth clients by `created`, tags by name.
- **Filters** are query parameters with exact values. Several filters must all match. A filter that matches nothing gives an empty list, not `404`.
- There is no sort parameter, no field selection and no filter language. The CLI filters and sorts what it shows, on the client (001, "Tables: columns, filter, sort").

### Values

| Kind      | On the wire                                                                                                                   |
| --------- | ----------------------------------------------------------------------------------------------------------------------------- |
| key names | lowerCamelCase: `lastSeen`, `approvedRoutes`                                                                                  |
| time      | RFC 3339 in UTC: `"2027-02-07T10:00:00Z"`. `null` when there is none. Never the year 1.                                       |
| duration  | not used. A request carries a time, not "90 days".                                                                            |
| text      | a string. `""` when unknown.                                                                                                  |
| list      | an array. `[]` when empty, never `null`.                                                                                      |
| enum      | a short string in lowerCamelCase: `"oidc"`, `"sshCheck"`. A client must accept values it does not know.                       |
| IP prefix | the real prefix: `"0.0.0.0/0"`, never a word such as `exit`.                                                                  |
| owner     | `{"user": {"id", "name", "displayName", "email"}, "tags": []}`. Exactly one side is filled. `null` when there is no owner.    |
| reference | a small object with the ID and the name: `{"id": "12", "name": "mynode"}`. `null` when there is none, as is an ID on its own. |

- **Every field is always present** in a response. A field is never left out because it is empty.
- **The name of a time field is the event**: `created`, `expiry`, `lastSeen`, `lastUsed`, `updated`, `revoked`. These are the words of the CLI.
- **The server computes a state.** An auth key has `"state": "used"`, a node has `"expired": true`. A client does not compare `expiry` with its own clock.

### Secrets

- The secret of an auth key, an API key or an OAuth client is in the answer to the create call, in the field `key`, and nowhere else. The server keeps only a hash of it, so it cannot be read again.
- Every other answer has the `prefix`: the short, public part of the key, as a plain string. It is never a masked text such as `hskey-auth-ab12cd-***`.

### Dry run

Two writes take `?dryRun=true`: `PUT /policy` and `DELETE /users/{id}`. A dry run runs every check of the real call, changes nothing, and answers with the same status and body the real call would give. An invalid policy is a `422` problem in a dry run too, never a `200`.

### Strictness

- An unknown field in a body is a `422`.
- An unknown query parameter is a `422` too. A typo such as `?usr=3` must not return every node.
- Every operation has a limit for the size of its body. A larger body is `too_large`.
- A client must ignore response fields it does not know. That is what lets the server add fields.

### Where each rule comes from

v0 follows the published standards and the large API guidelines. A reviewer can check each rule against its source.

| Rule                                                                      | Source                                                        |
| ------------------------------------------------------------------------- | ------------------------------------------------------------- |
| methods and status codes; `201` with `Location`; `204` with no body       | [RFC 9110]                                                    |
| `PATCH`, and its merge rules and media type                               | [RFC 5789], [RFC 7396]; Azure and Zalando ask for merge patch |
| the error body                                                            | [RFC 9457]                                                    |
| `ETag`, `If-Match`, `412`                                                 | [RFC 9110], section 13                                        |
| `Authorization: Bearer`; access tokens from client credentials            | [RFC 6750]; [RFC 6749], section 4.4                           |
| times                                                                     | [RFC 3339]                                                    |
| `Deprecation` and `Sunset`                                                | [RFC 9745], [RFC 8594]                                        |
| plural, flat collections; one ID, in the path                             | AIP-122; Zalando rules 134 and 141                            |
| a write returns the resource; no `PUT` of a whole resource                | AIP-134; Azure                                                |
| a list is an object, never a bare array                                   | AIP-158; Azure                                                |
| dry run                                                                   | AIP-163                                                       |
| a stable code in every error                                              | AIP-193; Azure; Stripe                                        |
| the secret of a key only in the answer to create                          | what Tailscale, NetBird and Defined Networking do             |
| reject what is unknown in a request; ignore what is unknown in a response | Zalando rule 108                                              |
| what counts as a breaking change                                          | AIP-180                                                       |

**Where v0 leaves the common rule, and why:**

- **Lists are not paged.** AIP-158 says every list is paged from its first release, because paging cannot be added later without breaking clients. That holds when paging is on by default. Here paging can only come as opt-in, so a client that does not ask keeps getting everything. See [Lists](#lists).
- **Actions are `/expire`, not `:expire`.** Google and Azure write `POST /nodes/12:expire`. The Tailscale API, GitHub and Stripe write `POST /nodes/12/expire`. Both are in wide use. v0 takes the form its users already know from the Tailscale API.
- **Time fields have no `At`.** Many guides write `createdAt`. v0 uses the words of the CLI: `created`, `expiry`.
- **One delete has a body.** [RFC 9110] allows `200` with a body for a `DELETE`. Only the user delete uses it.

## Errors

Every error is a problem (`application/problem+json`, RFC 9457) with a `code`.

```
HTTP/1.1 409 Conflict
Content-Type: application/problem+json

{
  "type": "https://headscale.net/stable/ref/api/problems/#user_has_nodes",
  "title": "The user still owns nodes",
  "status": 409,
  "code": "user_has_nodes",
  "detail": "User 3 (alice) still owns 3 nodes.",
  "requestId": "hs1/Zx81kq-000042",
  "object": {"kind": "user", "id": "3", "name": "alice"},
  "details": {
    "nodes": [
      {"id": "12", "name": "mynode"},
      {"id": "15", "name": "laptop"},
      {"id": "16", "name": "phone"}
    ]
  }
}
```

| Member      | Meaning                                                                                                           |
| ----------- | ----------------------------------------------------------------------------------------------------------------- |
| `code`      | a short, stable string. **This is what a program reads.** Changing a code is a breaking change.                   |
| `type`      | a link to the documentation of this code                                                                          |
| `title`     | a short text, the same for every error with this code                                                             |
| `status`    | the HTTP status                                                                                                   |
| `detail`    | a sentence for a person. It may change. A program must not read it.                                               |
| `object`    | the resource the error is about: `{kind, id, name}`. For `name_taken`, the one that has the name. `null` if none. |
| `requestId` | the ID of this request in the server log                                                                          |
| `errors`    | for `invalid_field`: one entry per field, `{location, message}`, for example `body.tags[2]`                       |
| `details`   | data for this code. The documentation of each code says what is in it.                                            |

**Rules:**

- An error never contains a database message or a Go error text, and it does not copy the request back. `details` holds only what the code documents.
- Every error a handler can return has a code. A `500` has the code `internal` and no more.
- Every operation names the problem schema and its codes in the OpenAPI document, so the generated client has `code` as a field.
- A path that does not exist and a method that is not allowed are problems too, not plain text.

| Status | Used for                                                              |
| ------ | --------------------------------------------------------------------- |
| 400    | a request that cannot be read: bad JSON                               |
| 401    | no credential, or one that is not valid                               |
| 403    | a valid credential that may not do this                               |
| 404    | the resource does not exist                                           |
| 405    | the path exists, the method does not                                  |
| 409    | the request is fine, but the state of the server forbids it           |
| 412    | `If-Match` did not match                                              |
| 413    | the body is too large                                                 |
| 415    | the body is not JSON                                                  |
| 422    | a field or a parameter is unknown, or has a value that is not allowed |
| 500    | a fault in the server                                                 |
| 503    | the server cannot answer now                                          |

**The codes of v0:**

| Code                     | Status | When                                                                                         | `details`               |
| ------------------------ | ------ | -------------------------------------------------------------------------------------------- | ----------------------- |
| `unauthorized`           | 401    | no credential, or it is unknown, expired or revoked                                          |                         |
| `forbidden`              | 403    | the credential may not do this: the token lacks the scope                                    | `scope`                 |
| `not_found`              | 404    | the resource does not exist, or no longer exists                                             |                         |
| `invalid_request`        | 400    | bad JSON                                                                                     |                         |
| `method_not_allowed`     | 405    | the path exists, the method does not                                                         |                         |
| `too_large`              | 413    | the body is over the limit of the operation                                                  |                         |
| `unsupported_media_type` | 415    | the body is not JSON                                                                         |                         |
| `invalid_field`          | 422    | a field or parameter is unknown, or has a value that is not allowed; `errors` names each one |                         |
| `empty_patch`            | 422    | a `PATCH` with no fields                                                                     |                         |
| `name_taken`             | 409    | the name belongs to another node or user; `object` is that one                               |                         |
| `user_has_nodes`         | 409    | user delete without `withNodes`                                                              | `nodes`                 |
| `user_managed_by_oidc`   | 409    | a change to a field the identity provider owns                                               |                         |
| `owner_conflict`         | 422    | a key with both a user and tags, or with neither                                             |                         |
| `tags_required`          | 422    | an empty tag list where one is needed                                                        |                         |
| `tags_not_permitted`     | 422    | tags that are not in the policy, or that the token may not give                              | `tags`                  |
| `scope_requires_tags`    | 422    | an OAuth client with a scope that needs tags, and no tags                                    | `scopes`                |
| `invalid_scope`          | 422    | a scope that does not exist                                                                  | `scopes`                |
| `expiry_required`        | 422    | a key with no expiry                                                                         |                         |
| `expiry_in_past`         | 422    | an expiry before now                                                                         |                         |
| `auth_request_kind`      | 409    | `register` on an SSH check, or `approve` on a registration                                   | `kind`                  |
| `update_refused`         | 409    | the node did not start the update                                                            | `reason`, `clientError` |
| `policy_invalid`         | 422    | the policy does not parse, does not validate, or fails its tests                             | `errors`, `failedTests` |
| `policy_read_only`       | 409    | `PUT /policy` when the policy is a file                                                      | `path`                  |
| `precondition_failed`    | 412    | `If-Match` did not match the stored policy                                                   |                         |
| `unhealthy`              | 503    | `GET /health` when a check fails                                                             | `reasons`               |
| `internal`               | 500    | a fault in the server; the server log has it                                                 |                         |

`update_refused` has `reason`: `notConnected`, `updatesNotAllowed`, `clientRefused` or `timeout`. With `clientRefused`, `clientError` is the text the Tailscale client sent.

## Authentication

**One header:** `Authorization: Bearer <credential>`. HTTP Basic stays in the Tailscale API only, where the Tailscale tools need it.

| Credential         | Looks like         | May do                                             |
| ------------------ | ------------------ | -------------------------------------------------- |
| API key            | `hskey-api-…`      | everything                                         |
| OAuth access token | `hskey-oauthtok-…` | what its scopes allow                              |
| the unix socket    | no credential      | everything; access to the socket is the credential |

- An access token comes from `POST /api/v2/oauth/token`, as today. That endpoint stays where the Tailscale tools expect it. One OAuth client works on both APIs.
- **Scopes are the ones that exist** (`hscontrol/scope`). v0 adds no scope names. Every operation says in the OpenAPI document which scope it needs.

| Operations                        | Scope to read        | Scope to write   |
| --------------------------------- | -------------------- | ---------------- |
| nodes, tags, auth requests        | `devices:core:read`  | `devices:core`   |
| `PUT /nodes/{id}/approved-routes` |                      | `devices:routes` |
| users                             | `users:read`         | `users`          |
| auth keys                         | `auth_keys:read`     | `auth_keys`      |
| OAuth clients                     | `oauth_keys:read`    | `oauth_keys`     |
| policy                            | `policy_file:read`   | `policy_file`    |
| API keys, config, debug           | `all:read`           | `all`            |
| `GET /whoami`, `GET /health`      | any valid credential |                  |
| `GET /version`                    | no credential        |                  |

- **A token is held to the rules of the Tailscale API.** The answer to each of these is `forbidden`:
    - An auth key or an OAuth client made with a token gets only the tags the token has, or tags those tags own in the policy.
    - A new OAuth client gets no scope that the token lacks.
    - A token cannot make a key for a user (`userId`), and cannot register a node to a user.
    - A token cannot make an API key. An API key may do everything, so only an API key or the socket can make one.
    - `DELETE /users/{id}?withNodes=true` needs `devices:core` as well as `users`.
- The OpenAPI document and the docs page (`/api/headscale/v0/openapi.yaml`, `/api/headscale/v0/docs`) need no credential.

### Who am I

`GET /whoami` describes the credential of the request. A web UI uses it to check a key the user typed in, and to know which key is its own. Today some web UIs list every API key and search for their own prefix.

```
GET /whoami

{
  "kind": "apiKey",
  "id": "2",
  "prefix": "tr81ysk2m4xq",
  "owner": {"user": {"id": "4", "name": "bob", "displayName": "", "email": ""}, "tags": []},
  "scopes": ["all"],
  "tags": [],
  "expiry": "2027-02-08T09:14:00Z"
}
```

`kind` is `apiKey`, `oauthToken` or `local` (the socket). For `local`, `id`, `prefix`, `owner` and `expiry` are `null`.

### CORS

Five of the web UIs run in the browser and call the API directly. A browser allows that only when the server sends CORS headers, or when the web UI comes from the same address as Headscale. Headscale sends no such headers today, so these projects tell their users to do one or the other with a reverse proxy.

- A new config list names the origins that may call the API. It is empty by default, and then nothing changes.
- There is no `*` default. This is an admin API.
- For a listed origin the server answers preflight requests. It allows `GET`, `POST`, `PUT`, `PATCH` and `DELETE` with the headers `Authorization`, `Content-Type` and `If-Match`. It exposes `ETag`, `Location`, `Headscale-Version`, `Deprecation`, `Sunset` and `Link`. Without that, browser code cannot read the `ETag` of the policy.
- An error answer has the same headers. Without them the browser hides the problem and shows a network error.
- No cookies are used, so no credentials mode is needed.

### Nodes

```
GET    /nodes                          ?user=<id> &tag=<tag>
GET    /nodes/{id}
PATCH  /nodes/{id}                     name, expiry
DELETE /nodes/{id}
POST   /nodes/{id}/expire
POST   /nodes/{id}/update-client
PUT    /nodes/{id}/tags                {"tags": [...]}
PUT    /nodes/{id}/approved-routes     {"routes": [...]}
```

```json
{
  "id": "12",
  "name": "mynode",
  "hostname": "ubuntu-vm",
  "fqdn": "mynode.example.com",
  "owner": {"user": {"id": "3", "name": "alice", "displayName": "Alice", "email": ""}, "tags": []},
  "ipAddresses": ["100.64.0.1", "fd7a:115c:a1e0::1"],
  "online": true,
  "lastSeen": "2026-11-10T09:14:00Z",
  "expiry": "2027-02-07T10:00:00Z",
  "expired": false,
  "created": "2026-07-13T08:02:00Z",
  "clientVersion": "1.82.0",
  "os": "linux",
  "approvedRoutes": ["10.0.0.0/8"],
  "availableRoutes": ["10.0.0.0/8", "192.168.0.0/24"],
  "servingRoutes": ["10.0.0.0/8"],
  "ephemeral": false,
  "registerMethod": "cli",
  "authKeyId": null,
  "machineKey": "mkey:ab12…",
  "nodeKey": "nodekey:cd34…",
  "discoKey": "discokey:ef56…",
  "attributes": {"ip:publicAddress": "203.0.113.7"}
}
```

| Field             | Notes                                                                                                                                                          |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `name`            | The name in headscale. Can be changed. The legacy API calls it `givenName`.                                                                                    |
| `hostname`        | What the node reports. Read-only. The legacy API calls it `name`.                                                                                              |
| `fqdn`            | `name` and the base domain, with no dot at the end. `""` when no base domain is set. Headplane reads the config file today to build it.                        |
| `owner`           | One user, or tags. For a tagged node `user` is `null`. There is no made-up `tagged-devices` user.                                                              |
| `ipAddresses`     | IPv4 first.                                                                                                                                                    |
| `online`          | Connected, or gone for less than the grace period.                                                                                                             |
| `lastSeen`        | The current time while the node is online. `null` if it never connected.                                                                                       |
| `expiry`          | `null` means the node never expires.                                                                                                                           |
| `expired`         | `true` when `expiry` has passed, by the server's clock.                                                                                                        |
| `clientVersion`   | The short version of the Tailscale client, `1.82.0`. `""` when unknown.                                                                                        |
| `os`              | `linux`, `windows`, `macOS`, … as the node reports it. `""` when unknown.                                                                                      |
| `approvedRoutes`  | Routes an admin or the policy approved.                                                                                                                        |
| `availableRoutes` | Routes the node offers.                                                                                                                                        |
| `servingRoutes`   | Routes the node serves to others now: approved, offered, and this node is the one chosen to serve them. Exit routes are included. One meaning in every answer. |
| `registerMethod`  | `authkey`, `cli` or `oidc`.                                                                                                                                    |
| `authKeyId`       | The ID of the auth key the node joined with, or `null`. Only the ID, not the key.                                                                              |
| `attributes`      | Node attributes, a map from name to value.                                                                                                                     |

**Filters:** `user` (a user ID; tagged nodes never match) and `tag` (nodes that have this tag).

**Update.** `name` and `expiry` can be changed.

- `expiry` takes a time in the future, or `null` for "never". A time in the past is `expiry_in_past`. To expire a node now, use the action.
- A `name` that another node has is `name_taken`, with that node as `object`.

**Expire.** `POST /nodes/{id}/expire` sets the expiry to the server's "now". The node must log in again.

**Update the client.** `POST /nodes/{id}/update-client` asks the node to update its Tailscale client. The answer is the node. When the node does not start, the error is `update_refused` and says why. The Tailscale API can only say "not found" here.

**Set tags.** `PUT /nodes/{id}/tags` replaces the tags of the node.

- A node that a user owns becomes a tagged node. Its owner changes from the user to the tags. This cannot be undone.
- An empty list is `tags_required`. A tagged node cannot go back to a user.
- Every tag must be in `tagOwners` of the policy, else `tags_not_permitted`.

**Set approved routes.** `PUT /nodes/{id}/approved-routes` replaces the approved routes. `[]` removes all. One exit prefix approves both `0.0.0.0/0` and `::/0`. The list replaces everything, also the routes that the policy approved by itself.

**Why tags and routes are not `PATCH` fields.** Setting tags changes the owner and cannot be undone. Approving routes needs another scope (`devices:routes`) than changing a name. Each is one clear operation with its own rules, and each matches one CLI command.

### Users

```
GET    /users                          ?name=<name> &email=<email>
GET    /users/{id}
POST   /users
PATCH  /users/{id}                     name, displayName, email, pictureUrl
DELETE /users/{id}                     ?withNodes=true &dryRun=true
```

```json
{
  "id": "3",
  "name": "alice",
  "displayName": "Alice",
  "email": "",
  "pictureUrl": "",
  "provider": "local",
  "providerId": "",
  "nodeCount": 3,
  "nodes": [
    {"id": "12", "name": "mynode"},
    {"id": "15", "name": "laptop"},
    {"id": "16", "name": "phone"}
  ],
  "created": "2026-07-01T10:00:00Z"
}
```

| Field        | Notes                                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------------------------ |
| `name`       | The stored username. It is not replaced by the email when it is empty, as the legacy API does.               |
| `provider`   | `local` or `oidc`. Never `""`.                                                                               |
| `pictureUrl` | One name. The legacy API uses `pictureUrl` in the request and `profilePicUrl` in the answer.                 |
| `nodeCount`  | Nodes this user owns. Tagged nodes do not count. Several web UIs compute this today from the full node list. |
| `nodes`      | The same nodes, as references.                                                                               |

**Filters:** `name` and `email`, exact. Both can be given. A username is not unique ([#3429]), so `?name=alice` can return more than one user.

**Create.** `name` is required. The server checks the username, that `email` is an email address and that `pictureUrl` is an absolute `http` or `https` URL. A name that is taken is `name_taken`.

**Update.** Any of the four fields. A user from OIDC cannot be changed: the identity provider owns those fields (`user_managed_by_oidc`).

**Delete.**

```
DELETE /users/3?withNodes=true

200 OK
{"nodes": [{"id": "12", "name": "mynode"}, {"id": "15", "name": "laptop"}, {"id": "16", "name": "phone"}],
 "authKeys": 2,
 "apiKeys": 0}
```

- The delete removes the user, the auth keys the user owns and the API keys the user owns. It does not remove tagged keys the user created. Today the API keys stay, without an owner.
- A user that owns nodes is not deleted (`user_has_nodes`, with the nodes) unless `withNodes=true` is given. Then the nodes are deleted too.
- It is one operation: all of it happens, or none of it.
- The answer says what was removed. This is the one delete that has a body.
- `dryRun=true` gives the same answer and removes nothing. A client shows it to the admin before it asks "are you sure?".

### Auth keys

```
GET    /auth-keys                      ?user=<id> &tag=<tag>
GET    /auth-keys/{id}
POST   /auth-keys
POST   /auth-keys/{id}/revoke
DELETE /auth-keys/{id}
```

```json
{
  "id": "7",
  "prefix": "ab12cd34ef56",
  "description": "CI runners",
  "owner": {"user": null, "tags": ["tag:ci"]},
  "createdBy": {"id": "4", "name": "bob"},
  "state": "valid",
  "used": false,
  "reusable": true,
  "ephemeral": true,
  "expiry": "2026-11-17T09:14:00Z",
  "created": "2026-11-10T09:14:00Z",
  "revoked": null
}
```

| Field       | Notes                                                                                                                               |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| `owner`     | The user, or the tags, that nodes joining with this key get. For a tagged key `user` is `null`.                                     |
| `createdBy` | The user that owns the credential that made the key, or `null`. The server sets it. It is not the owner.                            |
| `used`      | `true` when a node has joined with the key.                                                                                         |
| `state`     | `valid`, `used`, `expired` or `revoked`. `revoked` wins over `used`, which wins over `expired`. `used` means used and not reusable. |
| `revoked`   | When the key was revoked, or `null`.                                                                                                |

- **The list has every key**, also revoked ones, until the server removes them after `preauth_keys.revoked_retention`. No list of the legacy API returns a revoked key.
- **Create** takes `userId` or `tags`, exactly one (`owner_conflict`), and `reusable`, `ephemeral`, `expiry`, `description`. `expiry` is required (`expiry_required`). The answer is the key and the secret in `key`.
- **Revoke** makes the key unusable and keeps it in the list. It cannot be undone.
- **Delete** removes the key. Nodes that joined with it stay. One case is open: today the server only revokes an ephemeral key that a node still uses. See [Open questions](#open-questions).
- **Filters:** `user` and `tag` match the owner, not `createdBy`.

The legacy API has "expire" (which sets the expiry to now) and "delete" (which sometimes deletes and sometimes revokes). v0 has revoke and delete, and each does one thing.

### API keys

```
GET    /api-keys                       ?user=<id>
GET    /api-keys/{id}
POST   /api-keys
POST   /api-keys/{id}/expire
DELETE /api-keys/{id}
```

```json
{
  "id": "2",
  "prefix": "tr81ysk2m4xq",
  "owner": {"user": {"id": "4", "name": "bob", "displayName": "", "email": ""}, "tags": []},
  "state": "valid",
```

- `owner` has the owner shape, so that every key looks the same. `tags` is always `[]`. A key with no owner has `"owner": null`.
- The list has every key, also expired ones.
- `state` is `valid` or `expired`.
- **Create** takes `userId` (optional) and `expiry` (required). The answer is the whole key and the secret in `key`. The legacy API returns only the secret, so a client cannot know the ID of the key it made.
- **Expire** sets the expiry to the server's "now".
- **Delete** takes the ID. The legacy API can only delete by prefix.

### Auth requests

A node that wants to join without an auth key, or a user who must confirm an SSH session, waits for an answer. The auth ID is in the URL the node shows.

```
GET    /auth-requests/{id}
POST   /auth-requests/{id}/register    {"userId": "3"}
POST   /auth-requests/{id}/approve
POST   /auth-requests/{id}/reject
```

```json
{"id": "hskey-authreq-…", "kind": "registration", "hostname": "newlaptop", "source": null, "destination": null}
```

- `kind` is `registration` or `sshCheck`.
- A registration has the `hostname` that the node reports. An SSH check has `source` and `destination`, the two nodes, as references.
- **There is no list.** An auth ID is a secret that the node hands to one person. Who has the ID may see and answer the request. Nobody can browse them.
- **Register** answers a registration and creates the node for the user. The answer is the new node. It takes a user ID. The legacy API takes a username, which can match two users.
- **Approve** answers an SSH check. **Reject** answers either kind. Both answer `204`.
- A request that timed out is gone, and so is one that was answered. Both are `not_found`.
- The wrong action for the kind is `auth_request_kind`. Today "approve" on a registration reports success and the node has to start again.

### Policy

```
GET    /policy
PUT    /policy                         ?dryRun=true      If-Match: "<etag>"
POST   /policy/reload
```

```json
{
  "policy": "{\n  // comments are kept\n  \"acls\": [ … ]\n}",
  "updated": "2026-11-09T16:40:00Z",
  "mode": "database",
  "path": ""
}
```

- `policy` is the text exactly as it is stored: HuJSON, with its comments.
- `mode` is `database` or `file`. In file mode `path` is the file and `updated` is `null`.
- **No policy is not an error.** When nothing is stored, `policy` is `""`, and Headscale allows all traffic. The legacy API answers `500`.

**Set.** `PUT /policy` with `{"policy": "…"}`.

- The server parses the policy, checks it against the users and nodes it has, and runs the tests in it. A failure is `policy_invalid`, with every error and every failed test in `details`.
- In file mode the answer is `policy_read_only`, with the path.
- `dryRun=true` runs all of that and stores nothing. It works in file mode too, so a tool can check a policy before it writes the file.

**No lost updates.** `GET /policy` sends an `ETag` header. A client that sends it back as `If-Match` on `PUT` gets `412` (`precondition_failed`) when somebody else changed the policy in between. The header is optional: a script that only writes a file works without it. Every web UI that edits the policy today reads all of it, changes it and writes all of it back, with nothing to stop two admins from overwriting each other.

**The policy file is watched.** In file mode the server reloads the policy when the file is saved, as it does for the extra-records file. Nobody has to send a signal. A file that is not valid leaves the old policy in place, and the log says why.

**Reload.** `POST /policy/reload` reads the policy again from where it is stored, the file or the database, and applies it. It is the policy part of what `SIGHUP` does today, with one difference: the caller gets the result. The answer is the policy, or `policy_invalid`. A tool that writes the policy file can call it to learn at once whether the file was accepted. It is also the way to apply a policy after the database bypass of `headscale policy set` in 001, which writes to the database behind the server. `SIGHUP` stays. It also reloads the TLS certificate.

```json
{"tags": [
  {"tag": "tag:ci",    "inPolicy": true,  "nodeCount": 1, "nodes": [{"id": "13", "name": "builder"}]},
```

### Server

```
GET    /version
GET    /whoami
GET    /health
GET    /config
```

- **`GET /version`** gives what `/version` at the root gives today: version, commit, build time and Go version. It needs no credential, as today. Every v0 answer also has the header `Headscale-Version`. See [Version check](#version-check).
- **`/version` and `/health` at the root stay** as they are. Web UIs read `/version` before they have a key.
- **`GET /whoami`** is described under [Who am I](#who-am-i).
- **`GET /health`** answers `200` with `{"healthy": true, "databaseConnectivity": true}`, or `503` with the problem `unhealthy` and the reasons.

`POST /debug/nodes` with `{"userId", "authId", "hostname", "routes"}` creates a waiting registration for a made-up node. The integration tests use it through `headscale debug create-node`. It is in the OpenAPI document under the tag `Debug`.

## The CLI and the API

### One client

The CLI calls only v0, through one generated client (`gen/client/headscale/v0`). It calls neither the legacy API nor the Tailscale API. The rule in 001, "prefer v2, extend v1", is replaced by this.

### `--output json` is the API object

001 says that `--output json` is defined by the CLI and is not the API object. Its reason was that no API object had everything the CLI shows, so the CLI had to join two calls. With v0 that reason is gone.

**The CLI prints the v0 object.** It may do three things and no more:

1. Print the array of a list without the object around it. `headscale nodes list -o json | jq '.[].name'` works.
1. Print rows that are API objects for a view. `nodes routes list` prints nodes. `nodes tags list` prints the rows of `GET /tags`.
1. Print nothing where the API has no body.

The CLI does not rename a key, change its case or flatten a value. If the CLI needs another name or another shape, the API changes.

**The CLI prints the answer as it came.** For `--output json` it does not decode the answer into its own types and encode it again. A field that this build of the CLI does not know would be lost that way.

**One table engine.** For a table the CLI decodes the answer into the types of the generated client. Each resource declares its columns once, next to that type: the name, the field, how to show it and how to compare it. One piece of code turns any list of such objects into a table and does `--columns`, `--list-columns`, `--filter` and `--sort` for every command. No command has table code of its own. A new field in the API becomes a column with one line.

**A command prints what the API answers.** `nodes update-client` prints the node, `policy set` the policy, `users delete` what was removed. `auth approve`, `auth reject` and the other deletes print nothing.

**What this gives:**

- One vocabulary. `.lastSeen` is the same in `headscale nodes list -o json` and in `curl`.
- The CLI is a working example for anyone who writes a web UI.
- One reference. `--list-columns` names the API field behind each column. The OpenAPI document describes it.
- No second set of types and no converter per resource.

**The key of a column is its name in camelCase.** The column `last-seen` is the key `lastSeen`. A user can guess the key. That is why the API says `expiry` and `created`, not `expiresAt` and `createdAt`. Four columns of 001 have a short name and a longer key: `ip` is `ipAddresses`, `version` is `clientVersion`, `auth-key` is `authKeyId` and `count` is `nodeCount`. `--list-columns` shows the key of every column.

**What it costs:** a change to v0 is a change to the JSON of the CLI. 001 already says that the JSON "matches the binary that printed it" and can change in any release, so no promise is broken. If scripts need a stable JSON later, a versioned output can be added then, as Tailscale did for its CLI.

**What stays with the CLI:** tables, sheets, relative times, the word `exit` for the two exit prefixes, `--columns`, `--filter`, `--sort`, prompts and messages. `version -o json` has no API object and stays CLI-defined, in camelCase.

### Finding a target

The CLI turns a target such as `mynode`, `12` or `100.64.0.1` into one resource (001, "Targets and resolvers"). It lists the collection and matches on the client. On the socket that is one cheap call.

The API does not get the matching rules of the CLI. They would become a contract, and every change to them an API change. A `match` parameter can be added later without breaking anything.

### Version check

v0 may change between releases, and the CLI can talk to a server on another machine. A CLI and a server of different versions would not fail. The generated client would drop fields it does not know and fill missing ones with zero, and every node would be "offline".

- Every v0 answer has the header `Headscale-Version`.
- The CLI compares it with its own version before it reads the body. When the major or minor version differs, it stops with a message that names both versions.
- A server that has no v0 answers `404` without the header. The CLI then says that the server is too old.
- On the socket the two are usually the same binary. After an upgrade the server is the old version until it restarts, and the check says so.

### What changes for every project that moves

- **Status codes.** Creates answer `201` and deletes `204`. HeadControl and Headscale Manager count only `200` as success.
- **Error bodies.** `code` is a string and the text is `detail`. Most REST projects read `message`, and headscale-admin reads `code` as a number.
- **Enums.** `REGISTER_METHOD_CLI` becomes `cli`. headscale-piying filters on the old names.
- **Keys need an expiry.** Headplane can send none today.
- **A tagged auth key has no user in the request.** `userId` and `tags` together are `owner_conflict`. The server sets `createdBy` from the credential.
- **The proxy recipes.** The CORS examples of headscale-ui and Headscale UI allow no `PATCH`, and the one of headscale-ui no `PUT`. v0 uses both.
- **The `Deprecation` and `Sunset` headers** of the legacy API cannot be read by a browser project that goes through a proxy recipe, because the recipes the projects document do not expose them.

### What v0 does not solve for them

- **Server configuration and restart.** Headplane, Headscale Panel and unraid-headscale-admin. `GET /config` gives a read-only copy as YAML, with secrets removed. Whether it holds what these projects read was not checked.
- **Host information.** Headplane runs an agent for the OS version, the client version and the SSH host keys. v0 has `os` and `clientVersion`. The OS version and the SSH host keys stay with the agent.
- **Permissions.** Headplane, ouroboros and Headscale Panel check ownership themselves. `GET /whoami` is the first part of what they would need.
- **Moving a node between users.** headscale-ui and Headscale Manager still offer it.
- **The name of a user in the policy.** headscale-admin, Headscale UI and Headplane add `@` to a username by hand. v0 gives no such text. It is an [open question](#open-questions).
- **CLI output.** ouroboros and the local mode of unraid-headscale-admin parse `headscale -o json`. `--output json` becomes the v0 object, so both break. The local mode of unraid-headscale-admin never used gRPC.
- **Browser node login.** headscale-console, and Headplane for browser SSH, ask for CORS headers on Headscale for the node login traffic. The CORS list here is for the API paths. Whether it should reach those paths is an [open question](#open-questions).

## Versioning and deprecation

### What v0 promises

- v0 may change in any release, also in a way that breaks clients.
- Every breaking change is in `CHANGELOG.md`, under the heading "API v0". Nothing changes without a note.
- Where it is practical, an operation or a field is marked as deprecated for one release before it goes.
- The OpenAPI document has the version of the server that made it.

**A breaking change is:** removing or renaming an operation, a field, an enum value in a request or an error code; changing the type of a field; a new required field in a request; a new default; a narrower set of accepted values.

**Not a breaking change:** a new operation; a new optional field or query parameter in a request; a new field in a response; a new enum value in a response; a new error code on a new condition. Clients must be written to accept these.

### From v0 to v1

When the shape has not changed for a while and the CLI and the web UIs have used it, v0 becomes `/api/headscale/v1`. From then on a breaking change needs `/api/headscale/v2`. `/api/headscale/v0` answers for one more release.

### The end of the legacy API

| Release         | Legacy API `/api/v1`                                                                     |
| --------------- | ---------------------------------------------------------------------------------------- |
| the one with v0 | works as before. Every operation is marked deprecated. Every answer carries the headers. |
| the next        | works as before                                                                          |
| the one after   | removed                                                                                  |

- In the OpenAPI document of the legacy API every operation has `deprecated: true`, so the docs page shows it.
- Every answer of the legacy API has the headers `Deprecation` (RFC 9745) and `Sunset` (RFC 8594), and a `Link` to the migration guide. A web UI with its own server can show a warning from these. A web UI in the browser can read them only when its proxy exposes them.
- The server logs a warning the first time the legacy API is used after a start.
- `docs/ref/api.md` gets a migration guide: the table in [Coverage of v1](#coverage-of-v1), with examples.

## Not in this proposal

**Changing the server configuration through the API.** Headplane and Headscale Panel edit `config.yaml`, and then restart Headscale through Docker, Kubernetes or a signal. They also edit the extra-records file. That is a real need. It is also a design of its own: which keys can change while the server runs, how a change is validated, where it is stored when the config file is read-only. v0 has `GET /config` and `POST /policy/reload`. No path under `/config` is used for anything else, so writes can be added there.

**Permissions for a user.** An API key may do everything. Headplane keeps its own database with roles on top of that, and ouroboros and Headscale Panel check ownership themselves. A permission model in Headscale (a key that can only see its owner's nodes, roles) would remove that work and that risk. It is a large design. v0 has OAuth scopes, the `owner` of an API key and `GET /whoami`, which are the parts such a model would build on.

**Events.** Several web UIs ask for the full node list every 5 to 30 seconds. A stream of changes would be better. It is left out for now for two reasons: a browser's `EventSource` cannot send an `Authorization` header, so the usual way to do it does not work with a bearer token; and the server has a 30 second write timeout that a stream must get around. A later `GET /events` can send the same node and user objects that the lists return.

**More about a node.** Headplane runs its own agent on the tailnet to learn the OS version and the SSH host keys of a node. v0 has `os` and `clientVersion`. The rest of what a node reports about itself can be added field by field when a client asks for it.

**Paging, sorting and a filter language.** See [Lists](#lists).

**Update available.** 001 has a column `update-available`. The server does not know the newest Tailscale version, so the Tailscale API field behind it is always `false`. A node in v0 has `clientVersion` and no `updateAvailable`. Adding it means the server must fetch a version list from the internet.

**Statistics.** Traffic counters and uptime history. Headscale does not record them.

**Device approval ([#2176]).** The field `authorized` on a node and the actions for it are reserved, as in 001.

**Changing the owner of a node to a user.** A tagged node cannot go back to a user, and a node cannot move between users. If that comes, it is a new operation next to `PUT /nodes/{id}/tags`.

**The token endpoint.** `POST /api/v2/oauth/token` stays in the Tailscale API. v0 accepts the tokens it gives out.

## Open questions

1. **When is the legacy API removed?** The table says two releases after v0 ships. There is a tension: for those two releases the web UIs are asked to move from an API that does not change to one that may change in any release. Two ways out: the two releases start to count when v0 becomes `/api/headscale/v1`; or the part of v0 that replaces the legacy API is kept still from its first release.

1. **Does the CLI stop when the versions differ, or warn?** Stopping is safe. A warning is kinder to someone with a CLI one patch release behind. The proposal stops on a different minor version.

1. **API keys: expire or revoke?** An auth key is revoked and says `revoked`. An API key is expired "now" and says `expired`, while the CLI verb for both is `revoke`. A real revoke for API keys would make the two agree. The table that stores the keys has the column for it.

1. **Who owns the limits of an expiry?** v0 requires an expiry on every key and sets no upper limit. The CLI gives the defaults (1 hour for an auth key, 90 days for an API key). The Tailscale API caps an auth key at 90 days. Should v0 have a cap?

1. **"Admin key."** 001 says an API key with no owner "may do everything". In the server every API key may do everything. Either 001 drops the word, or an owned key is limited, which is the permission model this proposal leaves out.

1. **Expiry of a tagged node.** 001 leaves open what `expire` does to a tagged node. If the server refuses, the code is `expiry_not_allowed`.

1. **A tag that is not in the policy, on a new auth key.** The legacy API checks only the syntax. v0 could refuse it with `tags_not_permitted`, as it does for `PUT /nodes/{id}/tags`.

1. **The policy as a raw body.** `PUT /policy` takes JSON with the policy as a string. With `curl` that needs `jq -Rs '{policy: .}'`. Accepting `Content-Type: application/hujson` with the file as the body would be simpler by hand and gives the generated client a second method.

1. **The node that registers during a user delete.** Between the dry run and the delete, a node can join the user. The delete then removes a node the admin did not see. The proposal accepts this: the answer of the delete lists what was removed. The alternative is that the delete takes the expected node IDs and refuses when they differ.

1. **The name of the CORS config key**, and whether it lists origins for all three APIs or only for v0. Two projects also ask for CORS on the paths of the node login, for a Tailscale client in the browser.

1. **Deleting an ephemeral auth key that a node still uses.** Today the server revokes it and keeps it. In v0 it would then stay in the list as `revoked` after a `DELETE` that answered `204`. Either the delete really deletes, or it answers `409` and says to revoke.

1. **Who made a tagged node?** A tagged node has no user. The server still knows which user registered it. One web UI guesses that person from the name of the tag. A `createdBy` on the node, as on an auth key, would answer it.

1. **A user with no name, and the name the policy uses.** v0 gives the stored `name` and no longer puts the email there when it is empty. A user from OIDC can then have `"name": ""`. Three web UIs also build by hand the text that names a user in the policy (`alice@`). One more field with that text would solve both.

1. **`lastSeen` of an online node.** The proposal says it is the current time, as the Tailscale API does, so that `--filter 'last-seen>90d'` never matches a node that is online. The other choice is the stored time, with `online` next to it.

## Implementation notes

**Where it goes.**

- The package is `hscontrol/api/headscale/v0`. The folders match the paths: `api/v1`, `api/v2`, `api/headscale/v0`. Nothing is renamed.
- The generated client is `gen/client/headscale/v0`, from `make client`.
- The API is added in four places in `hscontrol/app.go`: where the Huma APIs are built in `Serve`, in `HTTPHandler()`, in `createRouter`, and in the mux of the unix socket, before the catch-all that sends everything to the legacy API.
- The unix socket serves v0 with local trust, as it serves the other two.
- v0 is written clean, on the state layer. Shared code is good: where it is cheap, a legacy handler becomes a thin layer that calls the same code as v0 and maps the answer to the old shape. That is a bonus and not a goal, because the legacy API goes away.

**Before the legacy API is frozen.** The check of the web UIs found two places where `/api/v1` in the tree differs from 0.29. They are not part of this proposal. They should be fixed before the release:

- `POST /api/v1/node/{nodeId}/expire` took `expiry` and `disableExpiry` as query parameters in 0.29. It reads them from the body now. A web UI that sends them in the query expires the node at once.
- `GET /api/v1/policy` in file mode answered with no `updatedAt` in 0.29. It answers with the year 1 now. [Headplane] uses the missing value to know that the policy cannot be edited.

**Order of work.**

1. The empty API: package, wiring, OpenAPI and docs paths, client generation, the problem type, the auth middleware.
1. Read operations, with the full objects.
1. Writes.
1. The CLI moves to the new client, command by command. This is the work of 001.
1. The legacy API gets its deprecation marks and headers.

**Rules for the Huma code.** Each was checked against Huma v2.40.0.

- **Register every operation with `huma.Register` and an explicit `OperationID`** (`listNodes`, `getNode`, `updateNode`). The short helpers build the ID from the full path, and the client method becomes `ListApiHeadscaleV0Nodes`.
- **Do not use `autopatch`.** Under a path prefix it documents the `PATCH` route and answers `405` on it. Write `PATCH` by hand.
- **`PATCH` fields use a small `Optional[T]` type**, not a Go pointer. With a pointer, a field that was left out and a field that is `null` look the same, and "clear the expiry" becomes "leave the expiry".
- **Do not change a package-level setting of Huma** (`huma.NewError`, `huma.DefaultArrayNullable`, `huma.ValidateStrictCasing`). All three APIs run in one process, and the setting would change the other two. Use field tags and v0's own types.
- **The problem type is v0's own**, with `code`, `object` and `details`. Errors that Huma makes itself, for validation, are turned into it by a transformer of the v0 API. The `value` member of Huma's errors is dropped: for an unknown field it holds the whole request body. Each operation declares this type as its error schema. The router's own answers for an unknown path and a wrong method are replaced, because they are plain text.
- **Every handler error goes through one mapping function.** An error that is not mapped becomes `internal`, without its text.
- **Set `RejectUnknownQueryParameters`.** It is off by default. Huma answers `422` for such a parameter.
- **Mark every list field `nullable:"false"`, and return an empty slice, never `nil`.** The tag only changes the schema. A test checks that no answer has `null` for a list.
- **The `ETag` of the policy is compared by hand**: a strong hash of the stored bytes, in quotes. Huma's helper for `If-Match` answers `412` to `If-Match: *`.
- **Generate the client from the OpenAPI 3.1 document**, with `nullable-type: true`. oapi-codegen reads 3.1 since v2.8.0, so the step down to 3.0 that the other two clients use is not needed. Without `nullable-type` the client cannot send `null`.
- **Read through the view types** (`NodeView`, `UserView`), never `AsStruct()`, as `AGENTS.md` says.

**Server work behind the API.** Most operations call code that exists. These need new code in `hscontrol/state` or `hscontrol/db`:

- a user delete that removes the nodes and the API keys in one database transaction, and a dry run of it. The node store in memory and the messages to the other nodes follow the commit.
- a user update for display name, email and picture, with the OIDC check that only the rename has today
- an owner for an API key at create (`State.SetAPIKeyUser` exists and only tests call it)
- the list of auth keys with revoked keys and their state
- the list of tags from the policy
- a watch on the policy file
- the reason a node refused an update, which is only in the log today
- reading one auth request
- recording when an API key is used; nothing writes `lastUsed` today
- errors with a type from the policy reload, which only logs today
- a node update that changes name and expiry together, or neither
- the checks on a new user: username, email, picture URL
- the token rules in [Authentication](#authentication) that the Tailscale API does not need

**Tests.**

- Each operation has a test in the package with `humatest`: the request, the status, the body.
- `hscontrol/servertest` runs the generated client against a real server.
- One test fails when an operation has no scope, no error codes or no explicit operation ID, in the way `hscontrol/api/v2/guard_test.go` does for the Tailscale API.
- One test fails when `hscontrol/api` calls `AsStruct()`.
- The OpenAPI document is checked in. A change to it shows in review, and CI fails when it is stale.
